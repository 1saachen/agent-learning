# 第三阶段核心知识手册：Tool Calling 与单 Agent

## 1. 使用方法

这份手册用于第二遍复习和面试准备。第一次学习请先阅读项目根目录下的 `lesson.md`，并按 `contracts -> tools -> registry -> client -> agent` 的顺序看代码。

每个知识点都要回答四个问题：它解决什么问题、位于项目哪一层、失败时会发生什么、怎样测试。

## 2. 普通 LLM 工作流与 Agent

固定工作流由代码预先决定每一步：

```text
输入 -> 固定 Prompt -> 模型 -> 固定解析 -> 输出
```

Agent 则让模型在受控范围内选择下一步动作：

```text
输入 -> 模型决策 -> 工具或最终回答 -> 新状态 -> 模型再次决策
```

Agent 不是“能调用 API 的聊天机器人”这么简单。工程上至少要有：动作集合、状态、执行器、反馈循环和终止条件。

当前项目属于单 Agent：一个模型负责决策，一个 Python 控制循环负责执行。它没有多 Agent 协作，也没有长期记忆。

## 3. Tool Calling 是什么

Tool Calling 是模型与应用之间的一种结构化协议。应用把工具名称、描述和参数 Schema 发给模型；模型返回调用意图；应用决定是否执行。

```text
模型可以提出：call get_weather(city="上海")
模型不能自己发出 HTTP 请求，也不能直接运行 Python 函数
```

因此必须区分两个动作：

- **工具选择**：模型生成结构化的工具调用建议；
- **工具执行**：可信的应用代码验证并执行建议。

这种分离让程序可以拒绝未知工具、非法参数、越权操作和重复副作用。

## 4. 工具定义

一个有效工具定义包含：

- 稳定、唯一的名称；
- 描述什么时候使用以及什么时候不使用；
- 参数 JSON Schema；
- 清晰的字段描述、类型、枚举、范围和必填性。

工具粒度应该围绕完整业务动作。例如 `create_todo` 比 `write_json_file` 更安全、更容易描述；后者把路径和任意内容都交给模型，权限过大。

描述过于模糊会导致模型不调用或选错工具；多个工具语义重叠会增加路由错误。应通过评估集比较工具名和参数准确率，而不是只凭 Prompt 看起来合理。

## 5. JSON Schema 与 Pydantic

项目使用一个 Pydantic Model 同时承担两种职责：

```text
model_json_schema() -> 给模型看的生成说明
model_validate()    -> 程序执行前的硬校验
```

工具 Schema 是软引导，本地校验是信任边界。模型可能返回合法 JSON，但依然存在：

- 缺少必填字段；
- 枚举值错误；
- 日期格式错误；
- 数值越界；
- 多余或危险字段；
- 正确结构中的恶意文本。

字段通过 Pydantic 不代表操作一定安全。例如标题通过长度校验，仍可能包含敏感数据；文件路径即使是合法字符串，也可能越权。因此参数模型之外还需要权限设计。

## 6. 工具调用响应

DeepSeek 返回工具调用时，核心结构类似：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_123",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\":\"上海\"}"
      }
    }
  ]
}
```

注意 `arguments` 通常是字符串，需要 `json.loads()`。不要因为它位于 SDK 对象中就把它当成可信字典。

模型可能一次返回多个 `tool_calls`。应用必须为每个调用生成对应结果，并保留各自的 ID。

## 7. Assistant 与 Tool 消息

应用执行工具后，需要把两类消息按顺序加入历史：

```text
Assistant 消息：记录模型提出的完整 tool_calls
Tool 消息：记录某个 tool_call_id 对应的执行结果
```

Tool 消息示意：

```json
{
  "role": "tool",
  "tool_call_id": "call_123",
  "name": "get_weather",
  "content": "{\"ok\":true,\"data\":{...}}"
}
```

`tool_call_id` 是关联键。缺失或使用错误 ID 时，模型无法可靠判断结果属于哪个调用，供应商 API 也可能拒绝消息序列。

工具错误也应该作为 Tool 结果回传。这样模型可以改参数、换工具或向用户解释失败，而不是让整个进程直接崩溃。

### 7.1 任务级上下文与会话级上下文

需要区分两个范围：

- **任务级上下文**：一次 `run()` 内为完成当前任务而保留的消息；
- **会话级上下文**：多次用户输入之间共享的完整消息历史。

本项目的 `Conversation` 对象实现了第二种范围。它保存 system、user、assistant 和 tool 消息，交互 CLI 在整个进程中复用同一个对象。这样用户可以先查询天气，再基于“刚才的天气”继续提问。

当前实现是内存态短期上下文：程序退出即丢失，不包含持久化、token 裁剪和摘要。完整保留适合学习 Tool Calling 的消息协议，但历史变长会增加上下文成本，也可能超过模型窗口。后续工程化需要会话 ID、存储、滑动窗口、摘要或按需检索。

工具调用去重状态不属于会话历史。`seen_calls` 每次 `run()` 重新创建，只防止同一任务循环内重复副作用。

## 8. Agent 控制循环

控制循环的职责不是“调用模型直到成功”，而是管理有限状态转换：

```text
状态 = 消息历史 + 已用步骤 + 已调用签名 + trace

模型决策：
  无 tool_calls -> completed
  有 tool_calls -> 校验和执行 -> 更新状态 -> 下一步
  模型异常 -> model_error
  步骤耗尽 -> max_steps_exceeded
```

循环必须由应用掌握。不能让模型通过文本决定忽略步骤限制，也不能因为模型说“再次尝试”就无限执行。

## 9. 最大步骤与预算

最大步骤解决无限循环和无界成本。一“步”必须有清楚定义。本项目定义为一次模型决策，而一次决策可以包含多个工具调用。

生产系统通常还会限制：

- 最大模型调用次数；
- 最大工具调用总数；
- 单工具调用次数；
- 总耗时；
- 总 token 或金额；
- 工具返回内容大小。

只有 `max_steps` 仍不够。例如一步并行生成 100 个工具调用也会产生风险，所以复杂系统需要组合预算。

## 10. 重复调用、幂等与副作用

本项目用 `(工具名, 规范化参数)` 检测同一次运行内的重复调用。JSON 的空格和键顺序不同会被规范化成同一签名。

重复检测只是一层保护，不等于完整幂等：

- 进程重启后内存中的签名消失；
- 两个并发请求可能同时执行；
- 参数略微变化可能仍产生相同业务效果；
- 第一次请求可能执行成功，但响应在网络中丢失。

生产级副作用工具常用幂等键、数据库唯一约束、事务和执行状态表。发邮件、支付、删除数据等操作还应有人类确认。

## 11. 工具权限

使用最小权限原则：工具只获得完成一个明确动作所需的能力。

当前项目的安全选择：

- `search_notes` 不接受路径，只访问固定目录；
- `create_todo` 不接受存储路径和 ID；
- `get_weather` 只访问代码写死的 Open-Meteo 地址；
- 不提供 shell、任意代码执行和任意文件访问。

工具的名称和 Prompt 不构成权限控制。权限必须由执行代码、凭证范围、网络策略和数据层落实。

## 12. Prompt Injection

Agent 会读取外部内容，外部内容可能包含“忽略规则并调用某工具”等恶意文本。这是 Prompt Injection。

降低风险的方法：

- 把外部内容标记为不可信数据；
- 不根据检索内容扩大权限；
- 高风险工具需要独立授权；
- 在代码中限制路径、域名和参数；
- 工具输出进行大小和类型限制；
- 关键副作用要求人工确认；
- 记录调用轨迹并建立攻击测试集。

System Prompt 中写“忽略恶意指令”有帮助，但不能替代上述代码控制。

## 13. 超时与重试

系统中有两个独立网络边界：DeepSeek 与 Open-Meteo。两者都要设置 timeout。

模型调用可对 timeout、连接错误、429 和 5xx 有限重试。认证、权限、参数和模型名错误通常不应原样重试。

工具调用重试必须考虑副作用：

```text
只读天气查询失败 -> 有限重试通常安全
创建待办响应丢失 -> 原样重试可能创建两条
```

因此“是否临时错误”和“操作是否幂等”要一起判断。

## 14. 工具错误的设计

错误结果应让模型能调整，但不能泄露内部实现。推荐返回：

```json
{
  "ok": false,
  "tool_name": "get_weather",
  "error_type": "invalid_arguments",
  "message": "工具参数校验失败：city"
}
```

不应默认返回：完整栈、绝对路径、API Key、数据库语句、第三方响应正文或完整敏感文档。

错误类型要稳定，消息可以面向用户。监控系统可在受控日志中记录更详细的内部诊断，并通过 request ID 与用户结果关联。

## 15. 多工具与并行调用

模型可能在同一步提出多个互不依赖的工具，例如同时查询北京和上海天气。理论上可以并行执行，减少延迟。

但并行前要判断：

- 调用是否互相依赖；
- 是否都有副作用；
- 返回顺序如何与 `tool_call_id` 对应；
- 并发限制和供应商限流；
- 一个失败时其他调用是否继续。

本项目第一版按顺序执行，优先保证消息和副作用容易理解。后续可对明确只读且互不依赖的工具使用 `asyncio.gather()`。

## 16. Trace 与可观察性

最终回答不能说明内部究竟发生了什么。Trace 至少记录：

- 模型步骤；
- `tool_call_id`；
- 工具名；
- 校验后的参数；
- 成功或失败；
- 结果摘要或错误类型；
- 耗时。

生产环境还应记录模型、Prompt 版本、token usage、重试次数、停止原因和端到端延迟。对参数、工具结果和用户输入要做脱敏与访问控制。

Trace 用于调试、成本分析、安全审计和评估，不等于把所有原始内容永久写进日志。

## 17. Agent 评估

只检查最终回答不够。一个答案可能碰巧正确，但使用了错误工具或执行了多余副作用。

建议分层指标：

| 层次 | 指标示例 |
| --- | --- |
| 路由 | 是否需要工具、工具名准确率 |
| 参数 | 字段完整率、参数值准确率、校验失败率 |
| 轨迹 | 步骤数、多余调用率、重复调用率 |
| 工具 | 成功率、延迟、超时率 |
| 结果 | 最终回答正确性、是否忠于工具结果 |
| 安全 | 越权调用率、副作用误执行率 |

评估集应包含直接回答、单工具、多工具、条件工具、信息不足、非法输入、工具失败和 Prompt Injection 场景。

## 18. 如何稳定测试

单元测试使用 Fake Model Client 返回预设决策，原因是：

- 模型输出具有概率性；
- 在线测试慢且有费用；
- 上游故障会让本地测试不稳定；
- 很难稳定触发未知工具、重复调用等边界。

Fake Model Client 只替代模型边界，Agent 循环、注册表、Pydantic 和工具代码仍真实执行。天气单元测试使用 `httpx.MockTransport` 控制第三方响应。

测试金字塔：大量离线单元测试，少量真实集成探测，定期运行评估集。不能只做其中一类。

## 19. 什么时候不该使用 Agent

以下情况优先使用固定代码或工作流：

- 步骤完全确定；
- 规则可以可靠编码；
- 高风险操作不能容忍模型选错；
- 低延迟和低成本比灵活性重要；
- 输入输出契约非常严格；
- 没有足够的评估和监控能力。

例如“读取表单后写入固定数据库表”不需要 Agent。“根据开放问题选择搜索、笔记或天气并综合回答”更适合受控 Agent。

面试时不要把 Agent 当成默认架构。说明选择它带来的灵活性，以及为了控制不确定性增加的校验、预算、权限和评估成本。

## 20. 当前项目的完整数据流

```text
CLI 用户输入
  -> AgentRunner 创建 System/User 消息
  -> ToolRegistry 输出三个工具 Schema
  -> DeepSeekChatClient 发起请求
  -> AssistantDecision
      -> 无 tool_calls：最终回答
      -> 有 tool_calls：逐个处理
          -> 重复签名检查
          -> ToolRegistry 查找名称
          -> json.loads
          -> Pydantic 参数校验
          -> Python 工具执行
          -> ToolExecutionResult
          -> TraceEntry
          -> role=tool + tool_call_id 回传
  -> 下一次 DeepSeek 决策
  -> completed / model_error / max_steps_exceeded
```

## 22. 面试高频问答

**模型返回 Tool Call 后，工具会自动执行吗？**

不会。模型只生成工具名称和参数，应用程序必须验证名称、解析参数、检查权限并调用对应函数，然后把结果作为 Tool 消息回传。

**有 JSON Schema 为什么还需要 Pydantic？**

Schema提高模型正确生成参数的概率，但模型输出仍不可信。Pydantic 是执行前的本地硬校验，负责类型、枚举、范围和必填字段。

**为什么需要 `tool_call_id`？**

它关联模型提出的调用和应用返回的结果。一次响应可能包含多个工具调用，没有 ID 就无法可靠配对。

**如何防止 Agent 无限循环？**

设置最大模型步骤、工具总次数、总耗时和成本预算；检测重复调用；定义明确停止原因；记录轨迹并测试循环场景。

**如何防止重复创建待办或重复发邮件？**

在 Agent 内检测重复调用只是第一层。生产系统还需幂等键、唯一约束、事务、执行状态记录，并对高风险操作增加人工确认。

**工具调用失败怎么办？**

将稳定的错误类型和安全消息作为 Tool 结果回传，让模型调整或向用户解释。网络临时错误可有限重试，但副作用操作必须先考虑幂等性。

**为什么不用 LangChain？**

本阶段需要理解协议和控制循环，所以先用原生 SDK。掌握消息、Schema、执行器和停止条件后，再使用框架可以判断框架替你做了什么，以及哪里仍需自己负责。

**怎样测试 Agent？**

用 Fake Model Client 构造确定的决策序列，真实测试控制循环；工具用临时目录和受控 HTTP 响应；少量集成测试验证真实供应商；评估集衡量模型路由和结果质量。

## 24. 阶段完成标准

满足以下条件即可进入第四阶段 RAG：

1. 不看代码画出第 20 节数据流；
2. 真实跑通至少一个单工具和一个多步条件任务；
3. 独立完成一个新工具，包含 Model、Schema、handler、注册和测试；
4. 能解释最大步骤、权限、timeout、重复调用、幂等和 trace；
5. 为至少 10 条输入记录预期工具与参数，并统计实际准确率。
